# SourceSpec function catalog (pilot)

Work on **one application root** containing `package.json` and `tsconfig.json`. Read its guidance, Git status, and any existing catalog before writing. This skill bundles a copy of the current SourceSpec function schema at `assets/functions.schema.yaml` and a TypeScript tool at `scripts/functions-catalog.ts`. Resolve these paths relative to this SKILL.md, not the application.

Install the skill's own pinned dependencies once: `pnpm --dir <skill-dir> install --frozen-lockfile`. From anywhere, pass an absolute app path:

```bash
pnpm --dir <skill-dir> exec tsx scripts/functions-catalog.ts --app /absolute/path/to/apps/api --write
pnpm --dir <skill-dir> exec tsx scripts/functions-catalog.ts --app /absolute/path/to/apps/api --check
```

`--write` creates/refreshes **only** that app's `.sourcespec/catalogs/functions-catalog.yaml`; `--check` never writes and fails if it differs or lacks exactly one blank line between consecutive function entries. This TypeScript/JavaScript adapter inventories all app-owned function definitions, including callbacks in tests/config. It excludes imported libraries, generated directories, and siblings. Each entry has `sourceScope: application | test | tooling | unclassified` describing the owning source, **not** whether its callback is a runnable test. The adapter uses file paths (`*.test.*`, `*.spec.*`, test directories, config files, and common source directories); unmatched paths remain `unclassified` for review. `sourceScope` is required; older catalogs without it are accepted only as migration input. Existing curated classifications survive refresh. Other languages need their own adapters, not filename rules baked into the schema. This adapter prefers the app's installed TypeScript version for type inference, falling back to its own pinned version when unavailable. Test declarations belong in the separate test catalog. IDs persist when the path, declared name, and enclosing context match; new entries get opaque IDs. Neither IDs nor links are call traces, completeness claims about Requirements, or proof that tests pass.

Review the diff after refresh. After either command, inspect the unresolved-scope report. If any source is genuinely ambiguous, ask the user about its listed IDs/locations and plausible ownership in one concise batch; don't silently leave it unresolved or guess. Apply their decision to the catalog, then rerun `--check`. The pilot **fails closed** if old IDs become unmatched, two functions have ambiguous identities, or a catalog entry fails the bundled schema. Before using `--write` on a catalog generated by another tool, run `--check` and verify all prior identities match; review any parameter/signature differences rather than dropping linked IDs. Reconcile a confirmed move/rename deliberately against all links before refreshing again; there is no automatic prune or cross-app matching yet. Do not remove a function simply because no Requirement links to it. Avoid staging/committing generated output without the user's separate authorization.

YAML/JSON Schema cannot validate whitespace in parsed records; the bundled schema documents the spacing convention, and `--check` enforces it on the serialized catalog. The schema is a snapshot bundled for the pilot. If SourceSpec's canonical `schema/functions.yaml` changes, compare it and update this copy deliberately rather than silently assuming they stay synchronized. Run `pnpm --dir <skill-dir> typecheck` and `pnpm --dir <skill-dir> test` for skill changes.
