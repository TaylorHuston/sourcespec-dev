# SourceSpec CLI

This CLI inventories TypeScript/JavaScript functions and tests, inventories SQLite physical structure from an explicitly supplied database, and validates authored Requirements and data-model maps against shared schemas installed in `~/.sourcespec/schema/`. Skills only tell an agent when to run it and which records and links to review.

From `spaces/sourcespec/`:

```bash
pnpm --dir cli install --frozen-lockfile
pnpm --dir cli test
node cli/scripts/install-local.mjs
node cli/dist/sourcespec.js sspc-functions probe --app /absolute/path/to/app
node cli/dist/sourcespec.js sspc-functions write --app /absolute/path/to/app
node cli/dist/sourcespec.js sspc-functions check --app /absolute/path/to/app
node cli/dist/sourcespec.js sspc-tests write --app /absolute/path/to/app
node cli/dist/sourcespec.js sspc-tests check --app /absolute/path/to/app
node cli/dist/sourcespec.js sspc-data-models probe --app /absolute/path/to/app --sqlite /absolute/path/to/disposable-schema.sqlite
node cli/dist/sourcespec.js sspc-data-models write --app /absolute/path/to/app --sqlite /absolute/path/to/disposable-schema.sqlite
node cli/dist/sourcespec.js sspc-data-models check --app /absolute/path/to/app --sqlite /absolute/path/to/disposable-schema.sqlite
node cli/dist/sourcespec.js sspc-requirements check --app /absolute/path/to/app
# Deliberately discard an existing catalog and regenerate it from current source:
node cli/dist/sourcespec.js sspc-functions write --app /absolute/path/to/app --force
node cli/dist/sourcespec.js sspc-tests write --app /absolute/path/to/app --force
node cli/dist/sourcespec.js sspc-data-models write --app /absolute/path/to/app --sqlite /absolute/path/to/disposable-schema.sqlite --force
```

Install the CLI first (below). The installer puts the `data-model-catalog`, `data-models`, `functions`, `operations`, `requirements`, and `tests` schemas in `~/.sourcespec/schema/`. All CLI checks and writes read those shared schemas; none copy schemas into an app. If an installed schema differs from the checkout's template, installation stops before modifying the CLI. Review the difference before replacing the schema explicitly and reinstalling.

`sspc-data-models` reads only SQLite schema metadata, never data rows, and never initializes an app or creates a database. Supply an existing, disposable schema-only SQLite file generated by the app's own initializer; the todo app's `npm run data-model:probe|refresh|check` scripts automate creation and cleanup. It writes `.sourcespec/catalogs/data-model-catalog.yaml` with tables, columns, constraints (including DDL), foreign keys, and indexes; `check` compares this inventory to the supplied database and validates any authored `.sourcespec/data-models/*.yaml` maps against the installed schema and physical references. Views, triggers, and virtual tables are not inventoried and cause a failure rather than being ignored. Normal writes refuse removed/renamed IDs, while `--force` discards them but still refuses broken authored maps. The catalog is derived navigation, not the authoritative DDL, semantic proof, or a migration-history check.

For a monorepo with a shared manifest and TypeScript config, use `sspc-functions <action> --project /absolute/repo --scope server` (or `--scope @root` for direct root tooling). The CLI uses the target project's TypeScript when available; fallback inference needs review. Normal writes fail closed on stale/ambiguous identities. `write --force` intentionally ignores the existing catalog and atomically replaces it with a freshly generated one, losing all prior IDs and curated metadata (descriptions, overrides, test kinds). It still rejects ambiguities in the current source; it never rewrites authored links. Back up the old file and review the new catalog and links before using `--force`. Neither mode claims that tests pass. `sspc-requirements check` validates authored Requirement shape, IDs, and catalog links without parsing application code, so it is language-neutral. Run `sspc-tests check` separately for JavaScript/TypeScript declaration discovery. Neither command generates Requirements or mappings or establishes semantic coverage.

To install or explicitly refresh the local executable, run `node cli/scripts/install-local.mjs` **after** installing CLI dependencies. It builds a package from this checkout and installs it only into `~/.sourcespec/`, refusing to modify an unfamiliar existing directory or executable. It does not change your shell configuration. Run `~/.sourcespec/bin/sourcespec` directly, or add `~/.sourcespec/bin` to `PATH`. The installed CLI reads shared schemas from `~/.sourcespec/schema/` and reads/writes catalogs only in the chosen app. The templates bundled with the package are build artifacts from `../schema/`, not a separate source of truth.

The CLI's own current-state map lives in `cli/.sourcespec/`: complete function and test inventories plus authored Requirements and Scenarios. The `cli/` package owns this scope (its pnpm workspace contains only `.`), not the whole SourceSpec repository. After building and installing the CLI, run these checks from the repository root:

```bash
app="$(pwd)/cli"
node cli/dist/sourcespec.js sspc-functions check --app "$app"
node cli/dist/sourcespec.js sspc-tests check --app "$app"
node cli/dist/sourcespec.js sspc-requirements check --app "$app"
```

Catalog links are navigation pointers, not coverage or test results.

The example todo app invokes the checkout's built CLI. Install it into `~/.sourcespec/` before running its checks (the checkout CLI also reads the installed schemas). CLI tests use disposable homes; they do not depend on or modify the user's installation.
