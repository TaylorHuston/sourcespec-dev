# Todo function-ID churn rehearsal — 2026-09-29

A controlled test of the **workspace-only** breadcrumb catalog skill against `example-apps/example-todo/`. The canonical todo source, existing function catalog, Requirements, schema, and SourceSpec skill copy were **not edited**. The source change in [source-change.patch](source-change.patch) was applied only to disposable `/tmp` copies; it is deliberately redundant to isolate identity behavior, not a product patch to apply.

## Baseline and edit

- Against the real todo app, `--identity-preview` found **134 definitions, 0 range fallbacks, 0 issues**. The workspace skill's existing `--check` passed 134/134. `--write-breadcrumbs` correctly refused to replace its existing curated catalog.
- A disposable copy without that existing catalog generated its initial breadcrumb YAML: 134 entries, `--check-breadcrumbs` passed, and all preview IDs exactly matched the original app's preview. We translated **only the copy** of `add-task.yaml` from the five relevant existing function IDs to the baseline breadcrumb IDs, and copied its test catalog. `requirements-check.mjs` passed (one Requirement, three Scenarios).
- Edit A duplicated the pure `todos.filter` expression inside `remaining` while preserving the value. Two anonymous callbacks acquired the **same semantic breadcrumb**, so both gained a range discriminator. Definitions rose to 135, range fallbacks to 2, and the original callback ID `fnv1-b730376885a57bd3e9427f4952ffe046` disappeared. The two new IDs were `fnv1-24d472684098e304afe4df99689d50bd` and `fnv1-eb31d00f4f97213a051e02ae452bddc3`. Nothing in the ID alone tells which, if either, retains a reviewed link to the earlier callback.
- Edit B renamed the Requirement-linked `App.addTodo` to `App.submitTask` and updated the submit reference without changing its body. `addTodo`'s baseline ID `fnv1-f9f28a157175329f22a76bf551e799df` became `fnv1-17d38e6e330e7953f2e2c7e7d10cc6bc`. The nested `setTodos` callback's ID also changed: `fnv1-8260d0bf543904b1eff7e27ed2fce8b0` → `fnv1-d02984bdc6d914bedc0a6ff3e39369c4`. After both edits, **131 of 134 original IDs** remained, three were unmatched, and four IDs were new (including the additional callback).

## What the checks actually caught

1. `--check-breadcrumbs` failed after each edit because the initial YAML was stale. `--write-breadcrumbs` refused to overwrite that YAML; it did not auto-transfer any ID or annotation.
2. The copy's `requirements-check.mjs` still **passed against the stale catalog**: its link check verifies references inside the YAML, not source freshness. This shows why CI needs **both** checks.
3. In a second disposable copy with a freshly generated *changed* breadcrumb catalog, `--check-breadcrumbs` passed, while `requirements-check.mjs` failed twice for the old `App.addTodo` ID in `add-task.yaml#task-added` and `#save-failed`. Those are genuinely dangling curated links until a person reviews the rename. The unlinked `remaining` callback churn produced no Requirement error, correctly: it is not evidence of missing behavior.
4. In the modified disposable app, `tsc --noEmit` and `vitest run src/App.test.tsx` passed (**10 tests**). They check behavior and types, not link continuity. The full todo suite was not run on the deliberately stale intermediate catalog; a normal `npm test` includes its original catalog checker and was not the appropriate way to test the opt-in provisional mode.

**Conclusion:** the new IDs are usable for first-generation inventory and catch staleness, but initial-only generation is not a refresh/reconciliation workflow. A future check should propose unambiguous old→new candidates and require review before transferring curated links. In a collision group, a range-based match can move or become indistinguishable after insertion/reorder; fail closed rather than silently choosing a successor. Existing canonical todo IDs and links remain untouched. The workspace pilot's fallback IDs also conflict with the canonical schema's current position-independence description until an explicit policy decision is made. No files were committed or pushed.
